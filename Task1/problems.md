# Анализ проблемных мест — «Будущее 2.0»

## Контекст

Компания «Будущее 2.0» — медицинский стартап, купивший банк. Данные хранятся в монолитном DWH на SQL Server 2008, бизнес-логика реализована в самом DWH, операторы клиник работают через PowerBuilder. Объём данных — сотни терабайт, формирование сложных отчётов занимает часы.

| № | Проблема | Описание | Бизнес-сценарии | Влияние |
|---|----------|----------|-----------------|---------|
| 1 | **Монолитный DWH на SQL Server 2008** | Вся бизнес-логика и трансформации данных — внутри DWH. Легаси-СУБД не поддерживается производителем. Добавление новых источников требует изменения ядра DWH. | • Подготовка отчётности<br>• Интеграция новых бизнес-направлений<br>• Внедрение финтех-продуктов | Рост time-to-market для любого нового отчёта или источника данных. Невозможность независимого развития доменов. |
| 2 | **Долгое формирование отчётов (часы)** | Сотни терабайт данных, каскад трансформаций, отсутствие современных MPP/SMP-движков. | • Управленческая отчётность<br>• Оперативный контроль клиник<br>• Аналитика финтех-операций | Задержка принятия управленческих решений на часы. Невозможность оперативно реагировать на изменения рынка. |
| 3 | **PowerBuilder — интерфейс операторов клиник** | Устаревшая технология (1990-е), сложно интегрировать, нет API, высокая стоимость поддержки. | • Работа операторов в клиниках<br>• Запись пациентов<br>• Доступ к медкартам | Риски стабильности, сложность добавления нового функционала, зависимость от узких специалистов. |
| 4 | **ESB на Apache Camel как единственная шина** | Нет поддержки event-driven архитектуры, сложно масштабировать, ограниченные возможности CDC и streaming. | • Интеграция ИИ-сервисов<br>• Подключение фармацевтических партнёров<br>• Обмен данными между доменами | Узкое горлышко при росте числа интеграций. Невозможность построить real-time пайплайны для ИИ. |
| 5 | **Отсутствие доменной декомпозиции** | Медицина, финтех, ИИ — в одном DWH. Нет границ ответственности. Изменения в одной области ломают другую. | • Независимое развитие финтех-направления<br>• Масштабирование ИИ-сервисов<br>• Подключение новых партнёров | Конфликты изменений, длительные регрессионные тесты, блокировки разработки. |
| 6 | **Нет self-service витрины данных** | Вся аналитика — через Power BI с кастомизациями. Бизнес-пользователи не могут получить отчёт без участия ИТ. | • Самостоятельная работа бизнес-аналитиков<br>• Ad-hoc аналитика<br>• Построение срезов под новые задачи | ИТ — бутылочное горлышко для любой аналитической потребности. Затраты на сопровождение кастомизаций. |
| 7 | **Локальная инфраструктура (on-premise)** | Ограниченные возможности масштабирования, долгий provisioning ресурсов, отсутствие геораспределённого резервирования. | • Рост объёмов данных<br>• Пиковые нагрузки отчётности (конец месяца/квартала)<br>• Disaster Recovery | Невозможность быстро нарастить мощности под новые бизнес-направления. Риски потери данных при сбое. |
| 8 | **Смешение медкарт и финансовых данных в одном DWH** | Compliance-риски: медицинские данные (чувствительные) и финансовые данные в одном хранилище без должной изоляции. | • Соответствие 152-ФЗ и отраслевым стандартам<br>• Аудит доступа к медицинским данным | Риски регуляторных санкций. Усложнение сертификации (ISO, PCI DSS) — медицинские карты не могут быть в витрине данных. |
| 9 | **Отсутствие Data Lakehouse / Data Mesh** | Нет единой платформы для batch и real-time данных. Нет практики data products и data contracts. | • ML/AI-аналитика (обучение моделей)<br>• Big Data-сценарии<br>• Сокращение трансформаций | Дублирование данных, несогласованность метаданных, сложность построения end-to-end пайплайнов. |
