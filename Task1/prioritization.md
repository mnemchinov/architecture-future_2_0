# Приоритизация проблем — MoSCoW

Метод: **MoSCoW** (Must have / Should have / Could have / Won't have).  
Приоритеты связаны с бизнес-целями: выручка, time-to-market, качество сервисов, снижение затрат.

---

## Must have (критично для запуска)

| № | Проблема | Привязка к бизнес-целям |
|---|----------|------------------------|
| 1 | Монолитный DWH на SQL Server 2008 | **Time-to-market** — без замены/дополнения DWH невозможно независимое развитие доменов и подключение новых партнёров. Блокирует интеграцию фармацевтики и электроники. |
| 2 | Долгое формирование отчётов (часы) | **Выручка, скорость принятия решений** — отчёты строятся часами → задержка управленческих решений → потеря рыночных возможностей. Критично для оперативного контроля клиник и финтех-операций. |
| 5 | Отсутствие доменной декомпозиции | **Выручка, скорость вывода продуктов** — пока клиника, финтех и ИИ в одном DWH, они блокируют друг друга. Домены — основа Data Mesh. |
| 6 | Нет self-service витрины данных | **Качество сервиса, снижение затрат** — бизнес-пользователи не могут строить отчёты без ИТ. Витрина — центральный артефакт целевой архитектуры. |
| 8 | Смешение медкарт и финансовых данных | **Регуляторный риск, качество сервиса** — нарушение 152-ФЗ, невозможность сертификации. Медицинские карты должны быть изолированы от витрины. |

**Почему Must have:** Эти проблемы напрямую блокируют бизнес-цели (промежуточное и финальное состояние). Без их решения запуск витрины данных и независимое развитие доменов невозможны. Медленные отчёты (№2) бьют по выручке — задержка управленческих решений критична для оперативного контроля.

---

## Should have (важно, реализовать после Must)

| № | Проблема | Привязка к бизнес-целям |
|---|----------|------------------------|
| 3 | PowerBuilder — интерфейс операторов | **Качество медицинского сервиса** — замена на современный веб-интерфейс повысит стабильность. Критично, но не блокирует витрину. |
| 7 | Локальная инфраструктура (on-premise) | **Снижение затрат, масштабирование** — облачная миграция даст эластичность. Можно начинать параллельно с Must have. |

**Почему Should have:** Важные проблемы, но не блокируют запуск витрины. Необходимы для финального состояния через год.

---

## Could have (желательно, но не критично)

| № | Проблема | Привязка к бизнес-целям |
|---|----------|------------------------|
| 4 | ESB на Apache Camel | **Time-to-market, качество интеграций** — замена на event-driven шину ускорит подключение партнёров. На первых порах Camel справляется. |
| 9 | Отсутствие Data Lakehouse / Data Mesh | **Инновации, качество аналитики** — внедрение Data Mesh и Lakehouse критически важно, но может быть реализовано поэтапно, начиная с Data Lakehouse. |

**Почему Could have:** Эти проблемы важны для долгосрочной архитектуры, но для промежуточного состояния (2 месяца) не являются блокерами. Data Mesh можно внедрять итеративно.

---

## Won't have (не в приоритете на этом этапе)

| № | Проблема | Привязка к бизнес-целям |
|---|----------|------------------------|
| — | Полная замена Power BI | Power BI де-факто стандарт, достаточно дополнить его витриной данных. Замена — затратная миграция без прямого бизнес-эффекта. |
| — | Уход от Microsoft SQL Server полностью | SQL Server останется как источник данных для legacy-отчётов. Но витрина и домены строятся на новых технологиях. |

**Почему Won't have:** Не влияют на достижение бизнес-целей в горизонте года. Ресурсы на эти проекты не выделяются.

## Сводка по этапам

| Этап | Что делаем | Какие проблемы закрываем |
|------|-----------|-------------------------|
| **0–2 мес.** (промежуточное состояние) | Декомпозиция на домены, архитектурное решение, изоляция медкарт, запуск Data Lakehouse + Analytics Engine | 1, 2 (начало), 5, 6 (начало), 8 |
| **2–6 мес.** | Запуск витрины данных, миграция PowerBuilder на Clinic Dashboard, облачная миграция (пилот) | 2 (завершение), 6 (завершение), 3, 7 |
| **6–12 мес.** (финальное состояние) | Замена ESB, полноценный Data Mesh, ML Pipeline Platform, self-service для аналитиков | 4, 9 |
