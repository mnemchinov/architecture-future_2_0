# Обоснование Terraform-конфигурации

## Выбор провайдера и региона

Провайдер **yandex-cloud/yandex** выбран в соответствии с требованиями бизнеса — Yandex Cloud обеспечивает соответствие 152-ФЗ, ISO 27001 и PCI DSS, что критично для медицинских и финансовых данных. Регион `ru-central1` обеспечивает локальность данных на территории РФ.

## Архитектура сети

**VPC** разделяет среду на две подсети в разных зонах доступности (`ru-central1-a`, `ru-central1-b`):
- **Зона A** — основная зона для K8s master, баз данных, bastion
- **Зона B** — резервная зона для отказоустойчивости (реплики PostgreSQL, брокеры Kafka)

**NAT-шлюз** предоставляет исходящий доступ в интернет для узлов без публичных IP (K8s ноды, базы данных), обеспечивая при этом изоляцию от внешней сети.

**Security Groups** реализуют принцип наименьших привилегий:
- `k8s` — открыт 443/TCP для внешнего доступа к API и 6443/TCP для kubectl из внутренней сети
- `db` — доступ только из внутренней сети (10.0.0.0/8) по портам PostgreSQL (6432), Kafka (9092), ClickHouse (8123)

## Вычислительные ресурсы

### Managed Kubernetes
Использование **Managed K8s** вместо самостоятельной установки кластера:
- **Скорость**: кластер создаётся за минуты, а не дни
- **Качество**: автоматические обновления control plane, мониторинг, автоскейлинг
- **Затраты**: не нужно платить за мастер-узлы (Yandex не тарифицирует master)
- **Масштабирование**: node group с фиксированным размером 3 ноды (4 vCPU, 16 ГБ RAM, 100 ГБ SSD) — достаточно для пилотного запуска; при росте нагрузки переключаемся на auto-scale

### Bastion VM
Jump-хост (2 vCPU, 4 ГБ RAM) для безопасного доступа к внутренним ресурсам. SSH-доступ разрешён только через bastion, что исключает прямой доступ к базам данных и Kubernetes API из интернета.

## Управляемые базы данных

### PostgreSQL (S3-C2-M8: 2 vCPU, 8 ГБ RAM, 100 ГБ SSD)
Выбран Managed PostgreSQL вместо самостоятельной установки:
- **Качество**: автоматический бэкап, мониторинг, репликация
- **Отказоустойчивость**: два хоста в разных зонах (A и B)
- **Затраты**: нет расходов на администрирование СУБД

### ClickHouse (S3-C2-M8: 2 vCPU, 8 ГБ RAM, 200 ГБ SSD)
Managed ClickHouse для витрины данных (Data Mart). Размер диска 200 ГБ — запас для аналитических запросов и агрегатов.

### Kafka (S3-C2-M8: 2 vCPU, 8 ГБ RAM, 100 ГБ SSD × 2 брокера)
Managed Kafka с двумя брокерами в разных зонах для отказоустойчивости event bus. Использование Managed Kafka избавляет от необходимости вручную настраивать ZooKeeper и контролировать здоровье кластера.

## Object Storage

Бакет **arch-lakehouse** — основа Data Lakehouse на Apache Iceberg. Данные доменов публикуются в Object Storage в формате Iceberg, откуда их потребляют ClickHouse и Airflow. Приватный доступ (acl = private), анонимный доступ запрещён.

## IAM

Два сервисных аккаунта с минимальными правами:
- `arch-sa-k8s` — роль `editor` для управления кластером (создание нод, балансировщиков)
- `arch-sa-storage` — роль `storage.editor` для работы с бакетом

Это обеспечивает разделение доступа и принцип наименьших привилегий.

## IaC-подход

Использование Terraform (Infrastructure as Code) обеспечивает:
- **Воспроизводимость**: один `terraform apply` воссоздаёт идентичную инфраструктуру
- **Версионирование**: конфигурация хранится в Git, все изменения проходят код-ревью
- **Масштабируемость**: добавление нового домена — пара строк в конфигурации (новая подсеть, DB-кластер, service account)
- **Аудит**: любое изменение инфраструктуры фиксируется в истории Git

## Примечание

Конфигурация не была применена к реальному облаку — отсутствует доступ к Yandex Cloud для выполнения `terraform apply`. Код написан в соответствии с документацией провайдера yandex-cloud/yandex и готов к использованию после настройки аутентификации (yc init или сервисный аккаунт).
