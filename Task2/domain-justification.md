# Обоснование разделения на домены

## Принципы разделения

Разделение системы на домены выполнено на основе **бизнес-способностей** (business capabilities) компании «Будущее 2.0» и **законов Демарко** (слабая связанность, сильная связность внутри домена). Каждый домен:

- Владеет своими данными и бизнес-логикой
- Развивается независимо от других доменов
- Имеет собственную команду и технологический стек
- Предоставляет и потребляет data products через Data Mesh

---

## Выделенные домены

### 1. Медицинский домен

| Атрибут | Значение |
|---------|----------|
| **Границы** | Всё, что связано с работой клиник: запись пациентов, электронные медкарты, расписание, диагностика, инвентаризация |
| **Команда** | Разработчики клиник (Java/Python), врач-методолог |
| **Ключевые данные** | Медкарты, истории болезней, исследования (НЕ входят в витрину данных), данные по персоналу, расписание |
| **Data Products** | `Пациент (визит, запись)`, `Исследование (результаты диагностики)`, `Расписание (слоты приёма)` |
| **Бизнес-сценарии** | Быстрая запись, точная диагностика, ведение медкарт |

**Почему отдельный домен:** Медицина — ядро бизнеса, с особыми требованиями к хранению данных (152-ФЗ), изоляции от витрины данных и интеграции с ИИ-сервисами. Отделение от DWH позволяет развивать клиники без влияния на финтех.

---

### 2. Финтех-домен

| Атрибут | Значение |
|---------|----------|
| **Границы** | Банковские услуги: платежи, кредиты, счета, транзакции, финтех-операции |
| **Команда** | Golang/Java-разработчики, банковские аналитики |
| **Ключевые данные** | Финансовая история, счета, кредиты, транзакции |
| **Data Products** | `Платёж (транзакция)`, `Счёт (баланс)`, `Кредитная заявка`, `Выписка` |
| **Бизнес-сценарии** | Финтех-операции, выдача кредитов, платежи за медицинские услуги |

**Почему отдельный домен:** Финтех куплен как отдельный бизнес (банк). У него своя регуляторная отчётность (ЦБ), специфические требования и скорость изменений выше, чем в клиниках. Независимость критична для выпуска новых финансовых продуктов.

---

### 3. ИИ-домен

| Атрибут | Значение |
|---------|----------|
| **Границы** | ML-модели, анализ медицинских изображений, NLP, предиктивная аналитика |
| **Команда** | Data Scientists, ML-инженеры (Python) |
| **Ключевые данные** | Анонимизированные данные исследований, результаты моделей, датасеты |
| **Data Products** | `Результат диагностики (модель)`, `Прогноз (аналитика)`, `Датасет (обучение)` |
| **Бизнес-сценарии** | ИИ-диагностика, анализ исследований, прогнозирование |

**Почему отдельный домен:** ИИ-сервисы имеют собственный жизненный цикл (эксперименты → обучение → деплой), требуют GPU-ресурсов и специфических пайплайнов. Отделение позволяет итеративно улучшать модели без блокировок со стороны других направлений.

---

### 4. Партнёрский домен

| Атрибут | Значение |
|---------|----------|
| **Границы** | Интеграция с внешними партнёрами: фармацевтика, производители электроники |
| **Команда** | Интеграционные разработчики, менеджеры партнёрств |
| **Ключевые данные** | Данные о лекарствах, спецификации оборудования, заказы и поставки |
| **Data Products** | `Спецификация_лекарства (препарат)`, `Спецификация_оборудования (устройство)`, `Поставка (заказ)` |
| **Бизнес-сценарии** | Подключение фармацевтических компаний, интеграция медоборудования |

**Почему отдельный домен:** Партнёры — это будущий рост компании (стратегия). Выделение домена позволяет подключать новых партнёров без изменений в других доменах. Каждый партнёр — отдельный data product.

---

### 5. Управленческий домен (Головной офис)

| Атрибут | Значение |
|---------|----------|
| **Границы** | BI-отчётность, KPI, управленческий учёт, финансовая отчётность |
| **Команда** | Бизнес-аналитики, BI-разработчики |
| **Ключевые данные** | Агрегированные показатели, дашборды, отчёты |
| **Data Products** | `Отчёт_KPI (показатели)`, `Дашборд (витрина)`, `Бюджет (план/факт)` |
| **Бизнес-сценарии** | Быстрая подготовка отчётности, принятие управленческих решений |

**Почему отдельный домен:** Головной офис — потребитель данных из всех доменов. Выделение домена снимает нагрузку на другие домены по формированию отчётности. Витрина данных (self-service portal) — ключевой артефакт этого домена.

---

## Как снижается зависимость от DWH

В текущей архитектуре **весь лендскейп завязан на монолитный DWH** (SQL Server 2008). В целевой:

| Было | Стало |
|------|-------|
| DWH содержит бизнес-логику всех направлений | Каждый домен содержит только свою логику |
| Изменение в отчётности требует изменения DWH | Data Products — через Data Mesh |
| Power BI кастомизации поверх DWH | Self-service витрина на основе Data Lakehouse |
| Легаси DWH — единственный источник истины | Data Lakehouse — единое хранилище; DWH — только исторические данные |

Каждый домен **владеет своей operational data store** (PostgreSQL/YDB) и экспортирует данные в Data Lakehouse через опубликованные data contracts. DWH остаётся только как источник исторических данных до полной миграции.

## Преимущества для бизнеса

| Преимущество | Описание |
|-------------|----------|
| **Ускорение time-to-market** | Каждый домен выкатывает изменения независимо — без согласования с другими командами |
| **Снижение зависимости от DWH** | Новая бизнес-логика не требует изменения legacy DWH — сразу реализуется в домене |
| **Независимое развитие направлений** | Финтех развивается со своей скоростью, ИИ — со своей, клиники — со своей |
| **Масштабирование для новых бизнесов** | Новый партнёр — новый data product в партнёрском домене, без доработки ядра |
| **Регуляторная изоляция** | Медицинские данные изолированы от финансовых — упрощается сертификация |
| **Гибкость технологического стека** | Медицина на Java, финтех на Golang, ИИ на Python — каждый домен выбирает инструменты под свои задачи |
